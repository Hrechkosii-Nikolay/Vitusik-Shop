# Vitusik Shop

Український магазин косметики: адаптивна вітрина, каталог, кошик, замовлення, кабінет, адміністративна панель, POS і спільний склад.

**Публічний сайт GitHub Pages — демонстрація.** Товари, бренди, склади засобів та контакти тестові; фотографії ілюстративні. Замовлення на Pages не передаються магазину. Демонстраційні дані зберігаються в браузері. Це не виробничий запуск усіх вимог ТЗ.

## Запуск повної локальної версії

Потрібен Node.js 24+. Зовнішніх npm-залежностей немає.

1. Скопіюйте `.env.example` у `.env`.
2. Заповніть `OWNER_EMAIL`, `OWNER_PASSWORD` (від 10 символів), `OWNER_NAME`.
3. Виконайте `npm start` і відкрийте http://localhost:3000.
4. Увійдіть у кабінет власника та відкрийте «Управління магазином».

SQLite створюється автоматично у `data/shop.sqlite`. Файл БД та `.env` виключено з Git. Паролі зберігаються як scrypt-хеші, cookie сесії має HttpOnly. На першому запуску додаються 10 тестових товарів. Власник створюється тільки через серверні змінні середовища, публічного стандартного пароля немає.

`npm test` — перевірки транзакцій, FEFO, повернень, статусів, закупівельних цін, авторизації та прав доступу.

## Що працює із сервером

- Пошук за назвою, брендом, артикулом та штрихкодом; категорії, бренди, ціна й наявність; ціни та акції.
- Реєстрація, вхід, вихід, профіль, історія замовлень, повторення замовлення, обране у БД та модерація відгуків.
- Онлайн-замовлення й POS використовують одну SQLite-БД. Залишок списується транзакційно при створенні замовлення. Клієнтський залишок періодично оновлюється, кожний продаж перевіряє актуальний залишок на сервері.
- Приходи, списання, коригування, історія рухів, постачальники, партії з термінами, FEFO, прострочені партії не продаються.
- Повернення відновлюють вихідні партії; скасування не зараховує залишок повторно. Історія статусів і журнал операцій.
- Закупівельна ціна останнього приходу; знімок ціни закупівлі у продажі; виручка, валовий прибуток, маржинальність, розподіл за брендами/категоріями та продавцями. Повернення зменшують показники.
- Ролі owner/admin/seller/customer перевіряються сервером. Продавець не отримує закупівельних цін та прибутку через API. Власник керує фінансовим доступом адміністратора.
- Сканер USB/Bluetooth, що працює як клавіатура: штрихкод + Enter у POS або на складі.

## Публікація

GitHub Pages публікує тільки папку `docs/`, що є копією `public/`. Після змін інтерфейсу виконайте `node scripts/sync-pages.mjs`, потім commit/push. Backend не входить до публічного вебкаталогу.

Для робочого магазину потрібен окремий сервер із постійним диском, HTTPS та резервними копіями. На ньому запустіть `npm start`. В `public/config.js` задайте `API_BASE` адресою API; у `.env` сервера — точний `PUBLIC_ORIGIN` сайту. Для різних доменів може знадобитися `COOKIE_CROSS_SITE=true`; краще розмістити API на піддомені власного домену, оскільки браузери можуть блокувати сторонні cookies. Оновіть `docs/` після зміни конфігурації. Параметр `?demo=1` примусово вмикає демонстрацію для локальної перевірки.

## Інтеграції та межі першої версії

Платіжний і SMS-провайдери ще не визначені. Онлайн-оплата вимкнена, платіжний модуль має контракт і явно відмовляє до налаштування. Перехід «Зібрано» створює один запис у черзі SMS; без провайдера запис має `not_configured` і не видається за доставлене SMS. Email-відновлення створює одноразовий токен та запис у черзі, але надсилання email потребує окремого провайдера. Відновлення токеном реалізоване на API й у формі.

Доставка Новою поштою зараз вводиться вручну; API-адаптер підготовлений окремим модулем. Секрети передаються тільки через серверні environment variables. Немає реальних операцій оплати/розсилок у демоверсії.

Потрібні перед реальним запуском: реальний асортимент і фото, контакти, вибір і підключення провайдерів, перевірка доставки SMS/email та платежів, HTTPS backend, резервні копії й відновлення, операційна перевірка продавцем. Партійний облік повної собівартості, ПРРО, бонуси, кешбек, промокоди, мультимовність і додаткові склади не реалізовані відповідно до меж першого етапу. Для кількох процесів/великих навантажень рекомендована міграція шару зберігання на PostgreSQL.
